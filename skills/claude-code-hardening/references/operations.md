# Operations and activation gate

## Local artifact workflow

Use Python 3.10+ on POSIX. All paths must be absolute, normalized and free of
symlink components. The workspace and OS home must exist. Spaces are supported;
pattern metacharacters in these paths are rejected rather than interpreted as
permission patterns. The output parent must already exist, be owned by the
current user and not be writable by other users. It must be outside the workspace
and credential paths. Do not use an active configuration filename.

Establish the actual home even if `CLAUDE_CONFIG_DIR` points elsewhere. The
helper's default credential catalogue is not discovery of custom stores.
Establish the CLI version through an already trusted installation's `--version`,
not by installing or running a downloaded program. No installed CLI is required
to exercise the helper with synthetic fixture paths.

Example commands from this skill's directory (substitute confirmed paths and
version; do not use the example paths literally):

```sh
python3 -B scripts/harden.py plan \
  --workspace /home/user/project --user-home /home/user \
  --claude-version 2.1.290 --mode development \
  --output /home/user/hardening-candidates/development-v1.json
```

`plan` is read-only. It returns a deterministic plan ID and the proposed settings.
The version input is an operator-supplied label, not native compatibility evidence.
For offline preparation without an installed CLI, omit `--claude-version`; the
reported version is `unknown`. This is never sufficient for native activation.
Review the output and destination before export:

```sh
python3 -B scripts/harden.py export \
  --workspace /home/user/project --user-home /home/user \
  --claude-version 2.1.290 --mode development \
  --output /home/user/hardening-candidates/development-v1.json \
  --plan-id PLAN_ID_FROM_THE_REVIEWED_PLAN

python3 -B scripts/harden.py verify \
  --workspace /home/user/project --user-home /home/user \
  --claude-version 2.1.290 --mode development \
  --output /home/user/hardening-candidates/development-v1.json
```

Export creates only the named candidate, with private file permissions. No
`~/.claude/settings.json`, `.claude/settings*.json`, managed settings, shell
startup files, credential helpers or skill-install directories are updated.
The artifact contains ordinary JSON, not JSONC. A stale plan or existing output
stops export. Use a new path for another revision. There is no force overwrite.

Verification compares exact generated bytes, not just a permissive JSON schema.
It does not start Claude, parse its effective settings, connect to a service or
run sandbox probes. An artifact mismatch must not be bypassed with a new hash
of the edited file. Generate and review a new candidate.

## Native activation gate

No native version has been certified in this repository. Complete this gate on
the intended platform before using a candidate for real work. Retain a concise,
sanitized record of the binary/version, platform, source classifications,
candidate hash and probe outcomes. A settings key existing in current docs is
not evidence that an older binary accepts or enforces it.

1. Identify every effective configuration source, including managed settings
   delivered by the organization and environment overrides. Do not print secrets
   from settings or read `.credentials.json` / `.claude.json` to discover them.
   Use product UI and human administration information where necessary. An
   unavailable source remains `REVIEW_REQUIRED` and blocks a verified claim.
2. Check inherited allow/ask/deny rules, extra write directories, exclusions,
   allowed domains, domain rules from WebFetch, Unix sockets, custom proxies,
   disabled filesystem isolation and weakening flags. Candidate empty arrays
   do not reset inherited lists. Do not use `--setting-sources` to silently
   discard user or project protections. Managed settings remain a distinct boundary.
3. Review hooks, MCP, plugins, LSP and helper commands separately. They can run
   outside the shell sandbox, including at startup. The candidate does not
   disable or certify them. If they cannot be assessed, stop activation.
   Specifically inspect mods handling `tool.check`: in personal sessions without
   managed settings or a Team/Enterprise login as the active credential, a mod
   can approve calls despite ask/deny rules. Such a mod invalidates this
   candidate's permission assumptions; stop activation pending separate review.
4. Check that the exact version supports every candidate key at CLI-settings
   scope. In particular, strict network allowlisting and auto-mode controls
   have scope/version restrictions. Reject schema warnings and ignored keys.
   Check Linux/WSL2 bubblewrap, socat and the Unix-socket seccomp filter through
   `/sandbox`; macOS uses Seatbelt. Dependency presence alone proves no isolation.
5. After authorization, start a fresh validation session from the confirmed
   workspace with the confirmed executable and `--settings` candidate:

   ```sh
   cd /home/user/project
   /absolute/path/to/claude --settings /home/user/hardening-candidates/development-v1.json
   ```

   This is a command to show the operator, not a helper action. Do not add
   bypass, auto, resume, extra-directory or exclusion flags. Check resolved
   settings in `/sandbox` and `/permissions`, and sources in `/status`.
   Changing workspace with `/cd`, adding directories or changing settings/plugins
   invalidates this review and requires another effective-source check.
6. Run the synthetic checks below only with authority for their local writes,
   session/model use and any requested network probe. Report individual outcomes.
   If blocked commands succeed, stop the session and investigate; do not use it
   for real work or call it hardened.

## Synthetic checks in the actual tool path

Use disposable files, never real credential contents or destructive commands.
Native validation can involve model/service use and is separate from the offline
helper tests. Do not use the `!` prompt or a standalone sandbox runtime as proof
of Claude Code's actual tool integration.

| Check | Expected observation |
| --- | --- |
| Read an ordinary fixture with Read | Allowed |
| Read a synthetic workspace `.env` with Read | Denied |
| Read that same synthetic `.env` using a Python subprocess in development | Denied by sandbox; do not test on real secrets |
| Request an edit of an ordinary fixture in development | Human approval required; permitted only after approval |
| Request an edit, Bash, PowerShell, Monitor or delegation in review | Denied / unavailable |
| Write a uniquely named fixture outside workspace and permitted temporary paths | Denied |
| Write a synthetic path covered by a metadata deny | Denied; do not modify real Git metadata to test it |
| Request a development shell command | Human approval flow; execution remains sandboxed |
| Reach an unapproved host with a harmless approved probe | Denied under the verified strict allowlist; no real payload |
| Attempt sandbox escape | Refused; never approve or retry unsandboxed |

Metadata and credential-catalogue checks that would touch real locations remain
`NOT_RUN` until an isolated fixture environment reproduces the target rules.
Do not equate a matching string in generated JSON with a passed denial probe.
Existing domain allows mean this policy is not necessarily offline. Even a
successful shell-network test says nothing about Claude's own API connection,
MCP, hooks, Web tools or other processes.

## Switching and recovery

Select a different scene by planning/exporting another file and repeating the
activation gate. Artifacts have no registration step and are never made defaults.
Existing sessions do not switch when another file is exported. After an update,
revalidate rather than reusing a previous runtime result.

To recover, stop the validation session and start without that candidate's
`--settings` argument, or select a previously verified candidate after checking
its current compatibility. Cleanup removes only the identified inactive
candidate on request. No recursive cleanup or session/history deletion is needed.
