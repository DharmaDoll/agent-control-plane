# Choose a recommended settings sample

Use the task's required capabilities to select a starting sample. The samples
are this repository's recommendations, informed by the
[cheatsheet and official documentation](sources.md); they are not upstream
named profiles or native-tested recipes.

## Selection

| Scenario | Sample ID | Shell / editing | Sandbox domains added by this sample |
| --- | --- | --- | --- |
| Understand source, review a diff already supplied, read documentation | `code-review` | Denied | None |
| Fix a bug, edit code, run local tests with existing dependencies | `local-development` | Human approval | None |
| Install public npm dependencies needed for development | `npm-dependencies` | Human approval | `registry.npmjs.org` |
| Install public PyPI dependencies needed for development | `pypi-dependencies` | Human approval | `pypi.org`, `files.pythonhosted.org` |

Ask only about missing capabilities that change the choice: whether commands
must run, whether dependencies are already installed, and which public registry
must be reached. Do not recommend registry access merely because `package.json`
or `pyproject.toml` exists. If dependencies are already present, prefer
`local-development` even for Node.js or Python work.

When presenting a recommendation, state the task fit, the permissions it adds,
what it still blocks, and the native verification status. Selection authorizes
neither package installation nor activation by itself. Use existing user
authorization rather than adding repeated confirmation prompts.

## Inspect the actual samples

From the installed skill directory:

```sh
python3 -B scripts/harden.py samples
```

This lists the fixed samples and their restrictions without reading user
configuration or requiring workspace/home/output arguments. Full settings are
generated by one builder in `scripts/harden.py`; there are no separate JSON
templates to drift out of sync. `plan --sample` renders the complete settings
with the confirmed paths. The snippets below show only differences for review,
and must not be applied as standalone replacements for the complete candidate.

### code-review

Example request: "Review these source files; do not execute project code or edit."

Choose `code-review`. Read/Grep/Glob remain subject to credential-path rules;
editing, Bash, PowerShell, Monitor and delegation are denied. This suits reading
an already supplied diff, but cannot run `git diff`, a test suite or a shell-based
scanner. If commands are needed, recommend `local-development` and explain that
it allows approved writes; do not promise a read-only shell.

### local-development

Example request: "Fix this bug and run the existing tests. Dependencies are installed."

Choose `local-development`. Shell and edit tools require human approval, and
sandbox/credential protections remain enabled. This sample adds no domain grants:

```json
{"sandbox": {"network": {"allowedDomains": [], "strictAllowlist": true}}}
```

An empty array does not revoke inherited grants, so call this "no new network
grants", not "offline". Builds needing downloads or host services can fail.

### npm-dependencies

Example request: "Prepare this project using its public npm dependencies, then test."

Recommend `npm-dependencies` if public registry retrieval is required. Relative
to `local-development`, the only settings change is:

```json
{"sandbox": {"network": {"allowedDomains": ["registry.npmjs.org"]}}}
```

It grants no GitHub, arbitrary binary-download, private-registry or wildcard
domains. `.npmrc` protection remains, so existing authenticated configuration
may prevent the command from working. Report that conflict instead of reading
tokens, changing registry/auth configuration or dropping the deny.

### pypi-dependencies

Example request: "Prepare a local environment with public PyPI dependencies, then test."

Recommend `pypi-dependencies` when public index/distribution access is needed.
Relative to `local-development`, the only settings change is:

```json
{"sandbox": {"network": {"allowedDomains": ["pypi.org", "files.pythonhosted.org"]}}}
```

It does not grant private indexes, Git dependencies or build-backend download
hosts. `.pypirc` and other credential protections remain. Do not copy credentials
into a workspace environment to make installation succeed.

### Restrictions common to dependency samples

Domain matching is not a GET-only rule, a package allowlist or a supply-chain
check. Approved shell processes can send data to those hosts; dependencies can
execute lifecycle/build code. No publish/upload authority is implied. Permission
to use a host says nothing about the safety of its packages.

Confirm the project's established lockfile and dependency workflow. Inspect
requirements for scripts, additional hosts, user cache writes and private
credentials before proposing commands. When local cache/virtual-environment
placement is needed, use an explicitly reviewed workspace or permitted temporary
location; the sample does not configure caches or add write access to the home.
Do not silently widen domains, write paths or sandbox exclusions after failure.

WebFetch, WebSearch, delegation, privilege escalation patterns, credential paths
and Git/Claude metadata remain restricted in every development sample. Choosing
a dependency sample does not grant those other capabilities.

## Render and select

For example, from the installed skill directory, with confirmed absolute paths:

```sh
python3 -B scripts/harden.py plan \
  --sample npm-dependencies \
  --workspace /home/user/project --user-home /home/user \
  --output /home/user/hardening-candidates/npm-v1.json
```

The output parent must already exist with the permissions required by
[operations.md](operations.md). Plan is read-only. Export and verify use the same
sample and paths; changing samples requires a fresh plan and a new file. A
plan made for local development cannot be exported as a dependency sample.

The original `--mode review` and `--mode development` remain aliases for
`code-review` and `local-development`. Their generated settings stay unchanged;
old plan IDs expire when the helper changes. Do not specify both selectors.

## Scenarios needing separate design

| Task | Why these samples are insufficient |
| --- | --- |
| Commit/push/PR operations | Git metadata and credential denies may block the workflow; host access alone does not define repository write authority. |
| Cloud administration or deployment | Requires service identity, target/resource permissions and an operation-specific execution boundary. |
| Private package registries | Requires reviewed endpoints and credential delivery; public-registry samples do not supply either. |
| Docker/host-service control | A socket or sandbox exclusion can expose broader host capabilities. |
| Unattended CI | These samples require interactive approvals and are not CI service-account policies. |
| Team-wide enforcement | Optional CLI settings are not administrator-controlled managed settings. |

For a mixed npm/PyPI task, explain the missing combined sample and review the
required capabilities separately; do not merge samples or add domains ad hoc.
The activation gate and runtime `NOT_VERIFIED` status apply to every sample.
